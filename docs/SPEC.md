## 1. מפת המודולים = סדר הטעינה

אין build. סדר התגים ב-`index.html` **הוא** גרף התלות. כל מודול הוא IIFE שמפרסם אובייקט אחד ל-`window`.

```
config.js     → CONFIG      קבועים, גרסה, מפתחות הגדרות
util.js       → U           מזהים, תאריכים, DOM, bidi, פורמט
kinds.js      → KINDS       רישום סוגי שדה: פורמט · ולידציה · העתקה
doctypes.js   → DOC_TYPES   טבלת סוגי המסמכים
db.js         → DB          IndexedDB
settings.js   → Settings    קריאה/כתיבה של הגדרות + מראת localStorage
vault.js      → Vault       שער PIN
files.js      → Files       נרמול קבצים, HEIC, גדלים, אווטאר
share.js      → Share       ייצוא קובץ החוצה: Web Share · הורדה · כרטיסייה
keyfile.js    → KeyFile     קובץ המפתחות: ייצוא, ולידציה וטעינה (§12.8)
versions.js   → Versions    זהות מסמך וגרסאות (§6.6)
expiry.js     → Expiry      מנוע התפוגה
search.js     → Search      חיפוש גלובלי על שדות
chat.js       → Chat        העוזר: הקשר, פרומפט, וקימפול פעולות (§14)
ui.js         → UI          toast, גיליונות, פרימיטיבים
forms.js      → Forms       DOC_TYPES → טופס ידני
screens.js    → Screens     ששת המסכים
app.js        → App         אתחול, ניתוב, היסטוריה, ארוע paste גלובלי
```

**כלל התלות:** מודול תלוי רק במי שנטען לפניו. `kinds.js` לא מכיר את `DB`. `doctypes.js` לא מכיר את `UI`. אם נוצרת תלות אחורה — המודול במקום הלא נכון.

`versions.js` יושב אחרי `doctypes.js` ולפני `db.js` — הוא קורא את הטבלה ואינו מכיר אחסון.
`share.js` אחרי `files.js`. `keyfile.js` אחרי `share.js` — הוא מכיר את `Settings`
ואת `KINDS`, ואינו מכיר מסך ואינו מכיר תחבורה. `chat.js` אחרי `search.js` ולפני
`ui.js` — הוא מכיר את ה-DB ואת הטבלה, ואינו מכיר מסך.

**נכסים סטטיים:** `fonts/assistant-hebrew.woff2` ו-`fonts/assistant-latin.woff2` — 29KB יחד, מתארחים עצמית. אין קריאה לשום דומיין חיצוני בזמן ריצה, וזה נבדק.

## 2. אחסון

IndexedDB בשם `DocVaultDB`, גרסה `1`.

| חנות | keyPath | אינדקסים | מסונכרן |
|---|---|---|---|
| `entities` | `id` | `by_updatedAt`, `by_sortOrder` | כן |
| `docs` | `id` | `by_entityId`, `by_typeKey`, `by_updatedAt`, `by_expiryDate` | כן |
| `blobs` | `id` | `by_docId` | **לא** — מקומי בלבד |
| `settings` | `key` | — | **לא** — מקומי בלבד |

`blobs` לעולם לא נכנס ל-`docvault-db.json`. `settings` לעולם לא עוזב את המכשיר — כולל מפתח Gemini, ה-hash של ה-PIN ומזהי הדרייב.

### 2.1 מזהים

```js
U.id = () => (crypto.randomUUID
  ? crypto.randomUUID()
  : Date.now().toString(36) + '-' + [...crypto.getRandomValues(new Uint8Array(8))]
      .map(b => b.toString(16).padStart(2,'0')).join(''));
```

הנפילה לאחור נחוצה ל-Safari ישן, שבו `randomUUID` חסר מחוץ להקשר מאובטח.

### 2.2 חותמות זמן

`updatedAt` הוא **epoch במילישניות** — `Date.now()`, מספר.

תחילה נקבע כאן ISO-8601, והוחלף אחרי תשובת נאביגו (Q4.6). הנימוק שהתקבל משם חזק
מהנימוק המקורי, והוא לא "התאמה" אלא נכונות:

`mergeSync` משווה `(a.updatedAt || 0) > (b.updatedAt || 0)`. הנפילה ל-`0` מבטיחה
שרשומה בלי חותמת תפסיד כל התנגשות. עם מחרוזות צריך `|| ''`, ואז `'' > '2026-…'`
הוא `false` **בשני הכיוונים** — רשומה בלי חותמת נתקעת ולא מסתנכרנת לשום כיוון.
בנוסף, epoch חוסך `Date.parse` בכל השוואה בלולאה.

`exported` בקובץ הסנכרון הוא `Date.now()` מאותה סיבה.

### 2.3 מחיקה רכה

`deleted` נשמר כ-`0` או `1`, לא כ-`true`/`false`. ⚠️ בוליאני אינו מפתח חוקי ב-IndexedDB, ורשומה מחוקה חייבת להיות ניתנת לסינון באינדקס. הסמנטיקה זהה.

**סכמת ה-tombstone** — ported from Navigo: `js/db.js:remove`. רשומה **מצומצמת**, לא רשומה מופשטת:

```js
docs      → { id, entityId, deleted: 1, updatedAt }
entities  → { id,           deleted: 1, updatedAt }
```

בדיוק המפתחות שהמיזוג ואינדקס ה-`entityId` צריכים. `entityId` הוא המקבילה ל-`tripId`
אצל נאביגו: בלעדיו רשומת ה-tombstone נופלת מהאינדקס ולא מסוננת החוצה.
כל השאר נמחק — אין סיבה שמספר תעודת זהות של רשומה מחוקה ימשיך להסתובב ב-`db.json`.

**גיזום tombstones: אין.** הם חיים לנצח. זו החלטה מנאביגו, לא פספוס: `db.json` של משפחה
אחת נשאר בסדר גודל של מאות קילובייטים, וגיזום מוקדם מדי הוא בדיוק המנגנון שמחזיר לחיים
רשומה שנמחקה במכשיר שהיה אופליין חודש.

ה-blobs של מסמך מחוק נמחקים מיד ומקומית — הם לא חלק מהסנכרון וממילא לא ניתנים לשחזור מרשומה מחוקה.

## 3. סכמות רשומה

### 3.1 `entities`

```js
{
  id:        'uuid',
  type:      'person' | 'vehicle' | 'home' | 'other',
  name:      'ליאור',
  color:     '#4B6B7A',        // מתוך פלטת אווטארים קבועה, לא בורר צבע חופשי
  avatar:      'ל',            // אות אחת. אימוג׳י אסור
  avatarImage: '' ,            // data URL של JPEG, צלע קצרה 256, או ריק. §17
  avatarFocus: { x: 50, y: 50 }, // מה מוצג בתוך העיגול, באחוזים. §17
  sortOrder:   0,              // מספר שלם, סדר ידני בתוך הקבוצה. §16
  updatedAt: '2026-08-22T09:14:03.221Z',
  deleted:   0
}
```

`color` נבחר מתוך שמונה גוונים מוגדרים ב-`CONFIG.ENTITY_COLORS`. הם נייטרלים־עמומים בכוונה ולא נגזרים מהאקסנט: אווטאר צבעוני שמתחרה בפלטה הופך את מסך הבית לרועש.

`avatarImage` גובר על `avatar` כשהוא קיים. הוא **data URL על הרשומה** ולא blob נפרד — הנימוק ב-§17.

### 3.2 `docs`

```js
{
  id:         'uuid',
  entityId:   'uuid',
  typeKey:    'vehicle_insurance',        // מפתח ב-DOC_TYPES
  title:      'ביטוח רכב',                 // ברירת מחדל: label של הסוג. ניתן לעריכה
  fields:     [ /* §3.3 */ ],
  issueDate:  '2025-11-02' | null,        // YYYY-MM-DD, יום לוח מקומי
  expiryDate: '2026-11-01' | null,
  files:      [ { blobId, driveFileId, mime, name, size, focusX, focusY, focusZ } ],
  source:     'upload' | 'camera' | 'paste' | 'drop' | 'chat',
  notes:      '' ,
  supersededBy: 'uuid' | null,          // הגרסה שדחקה את זו. §6.6
  sortOrder:  1000 | null,              // סדר ידני בתוך הישות. §16
  updatedAt:  '2026-08-22T09:14:03.221Z',
  deleted:    0
}
```

**`files[].focusX/focusY/focusZ`** הם המסגרת של התצוגה המקדימה בקובץ הראשון: שני צירים (0–100) והגדלה (1 עד `CROP_MAX_ZOOM`). ברירות המחדל — `50`, `0`, `1` — הן בדיוק מה שמסמך שנשמר לפני שהמסגרת הייתה קיימת כבר נראה, ולכן אין מיגרציה. **`focusZ` ברירת מחדל 1 ולא 0**; אפס שם פירושו תמונה שנעלמת.

הציר הרוחבי חי רק כשיש הגדלה — בהגדלה 1 תמונה גבוהה מהמסגרת נחתכת לאורך בלבד. שלושתם בחירה של המשתמש ולא ערך נגזר, ולכן הם **נוסעים בסנכרון**: מכשיר שני שמציג את אותו מסמך במסגרת אחרת נראה כמו באג. §15.

**`supersededBy` הוא מצביע קדימה בלבד.** השרשרת, "מי הנוכחי" ו"מהן הקודמות" נגזרים ממנו בזמן ריצה ואינם נשמרים. מסמך נחשב נדחק רק אם היורש שלו קיים — מחיקת היורש מחזירה אותו לתצוגה.

**`issueDate` ו-`expiryDate` אינם ב-`fields[]`.** הם עמודות עליונות כי מנוע התפוגה קורא אותן ישירות והאינדקס `by_expiryDate` בנוי עליהן. בכרטיס המסמך הם מוצגים כשורות שדה סינתטיות שהמרנדר מייצר — לא נשמרים פעמיים.

**פורמט תאריך:** `YYYY-MM-DD` בלבד, בלי שעה ובלי אזור זמן. תאריך תפוגה הוא יום לוח, לא רגע בזמן. שמירת `Date` מלא כאן היא המקור לשגיאת היום־האחד שמופיעה רק למשתמשים ממזרח לגריניץ׳.

**`source`** נרשם פעם אחת, במסלול שיצר את המסמך. הוספת קובץ שני במסלול אחר לא משנה אותו.

⚠️ `files[].size` נוסף לסכמה — גודל אחרי הנרמול, בבייטים. בלעדיו אי אפשר להציג "הצג את הגודל אחרי ההמרה" (§5 באפיון) בלי לטעון את ה-blob עצמו.

**`files[].blobId` הוא מזהה מקומי ואסור לו לחצות את המיזוג.**
המיזוג בשלב 5 הוא ברמת הרשומה — `{ ...remote }` דורס את המקומית כולה. אצל נאביגו יש
לכך חריג יחיד ומפורש, `if (lr && lr.blob) merged.blob = lr.blob`, בלעדיו כל סנכרון
מוחק את הקבצים מהמכשיר. אצלנו ה-blobs יושבים בחנות נפרדת, ולכן החריג לובש צורה אחרת
ומסוכנת יותר: רשומה מרוחקת נושאת `files[]` עם `driveFileId` אבל **בלי** ה-`blobId`
של המכשיר הזה, ודריסה תנתק את המסמך מהקובץ ששוכב אצלו בדיסק.

לכן, בשלב 5, המיזוג חייב למזג את `files[]` לפי `driveFileId` ולשמר את ה-`blobId`
המקומי לכל קובץ שכבר קיים כאן. זה החריג היחיד המותר במיזוג ברמת הרשומה.

### 3.3 `fields[]`

```js
{
  key:        'policyNumber',
  label:      'מספר פוליסה',
  value:      '2291043',
  kind:       'policy',
  sensitive:  true,
  confidence: 0.94 | null,     // מ-Gemini. null בהזנה ידנית
  verified:   true | false,
  multiline:  false            // ⚠️ הרחבה, §10.1
}
```

`label` ו-`kind` משוכפלים מהטבלה לתוך הרשומה בכוונה. מסמך שנשמר לפני שינוי בטבלה חייב להמשיך להיקרא נכון, וקובץ ה-JSON בדרייב חייב להיות מובן בלי הקוד. `DOC_TYPES` היא מקור האמת ליצירה; הרשומה היא מקור האמת לתצוגה.

**`verified` — כלל אחד, בלי חריגים:**

> בשמירה, `verified = true` אם ורק אם הערך עבר את הוולידטור של ה-`kind` שלו, או שאין ל-`kind` ולידטור. אחרת `false`.

הכלל חל זהה על הזנה ידנית ועל פלט Gemini. שדה עם `verified: false` מקבל תג "לאימות" ו**נשמר עם הערך שלו**. ספרה שגויה בת״ז גרועה מהיעדר ערך — אבל מחיקה שקטה גרועה משתיהן.

`confidence` נשמר ואינו מוצג. הסיגנל היחיד בממשק הוא `verified`. ⚠️ §10.4.

### 3.4 `blobs`

```js
{ id: 'uuid', docId: 'uuid', data: Blob, mime: 'image/jpeg', size: 184223 }
```

מאוחסן כ-`Blob`, לא כ-base64 ולא כ-`ArrayBuffer`. `Blob` ב-IndexedDB נשמר בדיסק ולא בזיכרון, ו-`URL.createObjectURL` עליו לא מעתיק את הבתים.

## 4. רישום סוגי השדה — `KINDS`

לכל `kind` חמש תכונות. אין `if` על שם סוג מחוץ לטבלה הזו.

```js
KINDS.id = {
  label:     'תעודת זהות',
  inputMode: 'numeric',
  sensitive: true,          // ברירת מחדל, ניתנת לדריסה ברמת השדה
  copyAs:    'canonical',
  canonical: v => v.replace(/\D/g, ''),
  format:    v => v.padStart(9, '0'),
  validate:  v => ({ ok: israeliIdValid(v), reason: 'ספרת ביקורת נכשלה' })
};
```

| kind | רגיש | copyAs | קנוני | תצוגה | ולידציה |
|---|---|---|---|---|---|
| `id` | כן | canonical | ספרות בלבד | ריפוד ל-9 ספרות | ספרת ביקורת ישראלית |
| `passport` | כן | canonical | אותיות+ספרות, רישיות | כמו הקנוני | `^[A-Z0-9]{6,9}$` |
| `plate` | לא | canonical | ספרות בלבד | `12-345-67` / `123-45-678` | 7 או 8 ספרות |
| `policy` | כן | canonical | ללא רווחים | כמו הקנוני | לא ריק |
| `date` | לא | **display** | `YYYY-MM-DD` | `DD/MM/YYYY` | תאריך אמיתי, שנה 1900–(היום+50) |
| `iban` | כן | canonical | ללא רווחים, רישיות | קבוצות של 4 | mod-97 |
| `phone` | לא | **display** | ספרות בלבד | `05X-XXX-XXXX` / `0X-XXX-XXXX` | 9 או 10 ספרות פותחות ב-0 |
| `text` | לא | display | trim | trim | לא ריק אם `required` |

**`copyAs` — הכלל וההצדקה:** מזהים מועתקים בצורתם הקנונית כי טפסים דוחים מפרידים; תאריכים וטלפונים מועתקים כפי שהם מוצגים כי זו הצורה שבן אדם מצפה לקבל בהודעה. אין נגיעה שמעתיקה את הצורה השנייה — ⚠️ נרשם ב-`DEBT.md` D1.

**`plate` אינו רגיש.** לוחית הרישוי מודפסת על הרכב ברחוב. מיסוך שלה הוא תיאטרון שמאמן אותך להתעלם מהמסכה.

### 4.1 ספרת ביקורת של תעודת זהות ישראלית

```js
function israeliIdValid(raw) {
  const s = String(raw).replace(/\D/g, '').padStart(9, '0');
  if (s.length !== 9) return false;
  let sum = 0;
  for (let i = 0; i < 9; i++) {
    let d = Number(s[i]) * (i % 2 === 0 ? 1 : 2);
    if (d > 9) d -= 9;                 // שקול לסכימת ספרות התוצאה
    sum += d;
  }
  return sum % 10 === 0;
}
```

`d - 9` שקול לסכימת ספרות של מכפלה דו־ספרתית, כי המכפלה לעולם אינה עולה על 18.
הריפוד לתשע ספרות נחוץ: תעודות ישנות מודפסות עם שמונה ספרות, והאפס המוביל הוא חלק מהמספר.

### 4.2 מיסוך

```
value.length > 4  →  '•••• ' + last 4
value.length ≤ 4  →  '••••'          // אין שארית לחשוף
```

חשיפה מחליפה טקסט בלבד. **ההעתקה קוראת תמיד את הערך המלא**, ללא קשר למצב המיסוך ולמצב הפרטיות.

## 6. מנוע התפוגה

### 6.1 נגזר בזמן ריצה, תמיד

**אין לשמור ערכים נגזרים.** אין `daysLeft` ברשומה, אין `bucket`, אין `status`. הם מחושבים בכל רינדור. מסמך ששמר "בעוד 12 יום" ונפתח שבועיים אחר כך משקר, ולא תהיה שום דרך לדעת.

### 6.2 חישוב

```js
function daysLeft(ymd, today = new Date()) {
  const [y, m, d] = ymd.split('-').map(Number);
  const exp = new Date(y, m - 1, d);            // חצות מקומי
  const now = new Date(today.getFullYear(), today.getMonth(), today.getDate());
  return Math.round((exp - now) / 86400000);
}
```

**חצות מקומי בשני הצדדים, ולא UTC.** בנייה מ-`new Date('2026-11-01')` מפרשת את המחרוזת כ-UTC, ומחזירה בישראל יום אחד פחות במשך שעתיים בכל יממה. `Math.round` ולא `floor` — שינויי שעון קיץ מזיזים את ההפרש ב-±שעה, ו-`floor` היה הופך את זה ליום שלם.

### 6.3 דליים

| דלי | תנאי | תווית |
|---|---|---|
| `past` | `daysLeft <= 0` | `פג היום` · `פג לפני N ימים` |
| `d30` | `1 ≤ daysLeft ≤ 30` | `בעוד N ימים` · `מחר` |
| `d90` | `31 ≤ daysLeft ≤ 90` | `בעוד N ימים` |
| `ok` | `daysLeft > 90` | `בתוקף עד DD/MM/YYYY` |

⚠️ **`daysLeft === 0` נכנס ל-`past`, לא ל-`d30`.** מסמך שפג היום עדיין תקף היום מבחינה פורמלית, אבל אם הוא מופיע ברשימת "עד 30 יום" הוא נקבר בין תשעה אחרים ואתה מגלה אותו מחר. יום התפוגה הוא היום שבו צריך לפעול.

מסמך עם `expiryDate === null` **אינו נכנס לרשימת התפוגות כלל**. הוא לא "תקין" ולא "חסר" — הוא פשוט לא מסמך שפג.

### 6.4 מסך התפוגות

**מסך הבית הוא ישויות (DEC-17).** המסך הזה הוא היעד של לשונית "תפוגות" בסרגל, והוא
נשאר המקום שבו רואים את התמונה המלאה. **הבאנר היומי (§6.5) יושב כאן רק אם המסך הזה
הוא מסך הבית**; כשמסך הבית הוא ישויות, מה שדורש טיפול נאמר בשורת המצב שבמסד (§16.2,
DEC-39) — אותה עובדה, בשורה אחת ובלי בר שצריך לסגור.

- קיבוץ לפי דלי, מיון פנימי לפי `daysLeft` עולה.
- דלי ריק אינו מוצג.
- `ok` מקופל מאחורי שורת `תקין · N מסמכים`. מסך הבית מציג בעיות.
- `ok` הוא ניטרלי, ללא צ׳יפ צבעוני — DEC-05.

### 6.5 התראה

אין backend, ואין push. **הממשק לא יבטיח התראה שלא תגיע** — אין מתג "קבל התראות", אין בקשת `Notification.requestPermission`.

בפתיחת האפליקציה, **כשמסך התפוגות הוא מסך הבית**: אם קיים מסמך ב-`past` או ב-`d30`, ומפתח `lastNoticeDay` אינו היום, מוצג באנר בראשו וה-מפתח מתעדכן. פעם ביום לכל מכשיר. הבאנר נסגר בנגיעה ואינו חוזר באותו יום.

**הבאנר לחיץ.** מסמך אחד לוקח אליו, כמה לוקחים לרשימת התפוגות. באנר שאומר "יש בעיה" ואי אפשר להגיע ממנו לבעיה הוא חצי מסר.

**הדחייה נזכרת לפי מה נדחה, לא רק לפי מתי.** לצד `lastNoticeDay` נשמר `lastNoticeSig` — רשימת המסמכים הדורשים טיפול ותאריכי התפוגה שלהם. מסמך שטופל יוצא מהחתימה; מסמך חדש שנכנס מחזיר את הבאנר גם באותו יום. בלי זה, "טיפלתי ובאנר עדיין שם" — וזה מאמן להתעלם ממנו.

### 6.6 גרסאות של אותו מסמך

טסט חדש אינו מסמך חדש. הוא **אותו מסמך, מעודכן** — וכל עוד המערכת אינה יודעת זאת, הישן ממשיך להופיע בתפוגות, ממשיך להדליק את הבאנר, וממשיך להיות מקור לגיטימי לשדות בהעתקה המהירה.

**הזהות נגזרת מהטבלה:** שדות ה-`required` של הסוג. `entityId` + `typeKey` + הערכים הקנוניים של שדות החובה. רישיון רכב מזוהה בלוחית, פוליסה במספר ובחברה, תעודת זהות במספר ובשם. הוספת סוג חדש לא מוסיפה שורה ל-`versions.js` — היא מביאה איתה את שדות החובה שלה.

חסר ולו שדה חובה אחד → הזהות היא `null`, ואין התאמה. בלי כל שדות החובה אין די ראיות כדי לקרוא לשני מסמכים "אותו מסמך", והשתיקה עדיפה על ניחוש.

**מי הגרסה הנוכחית:** תפוגה, ואז הנפקה, ואז `updatedAt`. התפוגה קודמת מפני שהיא מה שמייצר את הצורך — "מעודכן" הוא מה שתקף יותר, לא מה שהועלה אחרון. העלאה של מסמך **ישן** יותר נשמרת ומסומנת כגרסה קודמת, ואינה דוחקת את הנוכחי.

**מה נשמר:** `supersededBy` — מצביע אחד קדימה, על הרשומה שנדחקה. השרשרת נגזרת ממנו בזמן ריצה. אין ערך נגזר שנשמר, ואין שכפול של הרשומה.

מסמך נחשב נדחק **רק אם היורש שלו קיים**. מחיקת היורש מחזירה את הקודם לתצוגה, במקום להעלים את שניהם.

הכתיבה היא `DB.supersede` — טרנזקציה אחת שכותבת את החדש ומסיטה את הישנים. כישלון באמצע לא משאיר שתי גרסאות שתיהן נוכחיות.

**מה זה משנה בממשק:** `Screens.state.live` הוא הגרסאות הנוכחיות בלבד, וכל מסך שמציג נתונים קורא אותו — תפוגות, העתקה מהירה, רשימת המסמכים של ישות, והקשר העוזר. הגרסאות הקודמות נשמרות, מקופלות במסך הישות, ומקושרות מכרטיס המסמך לשני הכיוונים.

## 7. מסלולי הקלט

ארבעה מסלולים, **צינור אחד**. אף מסלול לא כותב ל-DB ישירות.

```
מסלול → File[] → Files.normalize() → מצע (staging) → פרסינג? → מסך אישור → DB.saveDoc()
```

| מסלול | טריגר | `source` |
|---|---|---|
| בחירת קובץ | `<input type="file" accept="image/*,application/pdf" multiple>` | `upload` |
| מצלמה | אותו input עם `capture="environment"` | `camera` |
| הדבקה | `paste` על `document` | `paste` |
| גרירה | `dragover`/`drop` על מעטפת האפליקציה | `drop` |

**השיוך נגזר מהמסלול שממנו הגיע הקובץ** (DEC-45). `App.entityContext()` מחזיר את
הישות כשהמסך הוא `#/entity/<id>`, את השיוך שכבר נבחר כשהטופס פתוח ב-`#/doc/new`,
ו-`null` בכל מסך אחר. שלושת מסלולי הכניסה למסמך חדש — גיליון ההוספה, גרירה
והדבקה — מציבים ממנו את `pendingEntityId`, ו-`Forms.doc` נופל ל-`entities[0]` רק
כשאין הקשר בכלל.

### 7.1 הדבקה — שני מסלולי משנה, ושלוש דרכים להגיע אליהם

הקלט נבדק בסדר הזה:
1. תמונה בלוח → מסלול תמונה.
2. אחרת, טקסט לא ריק → **מסלול טקסט**: נשלח לפרסינג ללא תמונה, ונוצר מסמך ללא קובץ.
   זו הדרך להכניס פרטי פוליסה שהגיעו בהודעה, בלי לצלם מסך.

**שלוש דרכים להגיע לשם, ופונקציה אחת שמטפלת בכולן** (`App.ingestPaste`):

| דרך | מתי |
|---|---|
| `Ctrl+V` על כל מסך | מקלדת, מהיר |
| **כפתור "הדבקה מהלוח" בגיליון ההוספה** | הדרך היחידה שגלויה בנייד |
| יעד הדבקה ידני | נסיגה כשהדפדפן חוסם קריאת לוח |

**הכפתור הוא התיקון לפער אמיתי:** ההדבקה עבדה מהיום הראשון דרך `Ctrl+V` בלבד, וזו
דרך שאינה קיימת בנייד ושאיש לא מנחש. מסלול שקיים ואינו גלוי הוא מסלול שאינו קיים.

הכפתור קורא `navigator.clipboard.read()` בתוך המחווה. איפה שזה חסום או לא נתמך —
נפתח יעד הדבקה עם מסגרת מקווקוות צבעונית, ולא נשאר כפתור שלא עושה כלום.

**מה שה-Clipboard API האסינכרוני אינו יודע לעשות, ואי אפשר לעקוף:**
הוא מוסר רשימת טיפוסים מסוננת — `text/plain`, `text/html`, `image/png`.
**`application/pdf` אינו ברשימה ולעולם לא יחזור ממנו**, ולא משנה מה יש בלוח בפועל;
אפילו `clipboard.write` דוחה אותו במפורש. יש על כך בדיקה שמריצה את הדחייה הזאת מול
הדפדפן, כדי שההנחה לא תישחק בשקט.

**קובץ מגיע רק דרך אירוע `paste` אמיתי**, שנושא `DataTransfer.files` — כלומר
`Ctrl+V` על מסך, או הדבקה לתוך יעד ההדבקה. שני המסלולים האלה עובדים, ויש עליהם בדיקה.

לכן כשהכפתור אינו מוצא תמונה ואינו מוצא טקסט בר-פרסינג, הוא **אינו מסתיים בהודעה**
אלא ביעד ההדבקה — המקום היחיד שבו הדבקת PDF באמת עובדת — עם הסבר שאומר את זה.
שתי הנסיבות מקבלות שתי הודעות: "הדפדפן חסם" ו"הלוח לא הכיל קובץ" מובילים את המשתמש
לשני דברים שונים לנסות.

`App.ingestText` מחזירה `true` **רק כשהיא באמת פרסרה**. טקסט שאין לו הסכמת פרסינג
אינו "טופל", והקורא צריך לדעת את זה כדי להציע מסלול אחר במקום לבלוע.

### 7.2 נרמול קבצים

```
PDF                        → עובר כמו שהוא, ללא נגיעה
תמונה ≤ 2400px וגם ≤ 800KB → עוברת כמו שהיא
כל תמונה אחרת (כולל HEIC)  → createImageBitmap → canvas → JPEG q0.85, צלע ארוכה 2400px
JPEG שיצא גדול מהמקור      → המקור נשמר במקומו
```

**המימדים ידועים רק אחרי פענוח**, ולכן `createImageBitmap` רץ תמיד — גם על תמונה שבסוף תוחזר כמות שהיא. בדיקת משקל בלבד הייתה מחמיצה צילום 3000px ששוקל מעט.

**הכלל האחרון אינו קישוט.** JPEG על תמונה סינתטית — צילום מסך, מסמך סרוק בשחור-לבן, שטחים אחידים — יוצא גדול מ-PNG המקורי, לפעמים פי עשרה. נרמול שמשמין קובץ הוא נרמול שגוי. הכלל חל רק כשהמקור כבר עומד בתקרת המשקל; תמונה כבדה תומר גם אם התוצאה אינה קטנה יותר, כי שם הבעיה היא המימדים.

HEIC אינו נתמך ב-`<img>` בכרום ובפיירפוקס, אבל **`createImageBitmap` מצליח עליו ב-Safari** — שם הוא מגיע מהמצלמה. אם `createImageBitmap` נכשל, הקובץ נדחה עם הודעה מפורשת ולא נשמר שבור.

הנרמול חל על **כל** התמונות ולא רק על HEIC. צילום של 12MP הוא 4MB; מאה מסמכים כאלה הם 400MB ב-IndexedDB ובדרייב. 2400px היא רזולוציה שבה מספר תעודה עדיין נקרא בזום.

הגודל **אחרי** הנרמול מוצג בשורת הקובץ ונשמר ב-`files[].size`.

### 7.3 מצע לפני שמירה

בין הנרמול למסך האישור, הקבצים יושבים בזיכרון בלבד. **אין כתיבה ל-DB עד אישור.**
נטישת המסך משחררת אותם ומבטלת `URL.createObjectURL` שנוצר.

הנימוק: מסמך חצי־מפורסס שנשמר "כדי לא לאבד" הוא בדיוק המסמך שאף פעם לא תחזור לתקן, והוא יושב ברשימת התפוגות עם תאריך שגוי.

### 7.4 שמירה

```
1. ולידציה של כל שדה → קביעת verified לכל אחד (§3.3)
2. יצירת/עדכון רשומת docs עם updatedAt חדש
3. כתיבת ה-blobs עם docId
4. שלב 5: הכנסה לתור הסנכרון
```

הכל בטרנזקציית IndexedDB אחת מעל `docs` ו-`blobs`. כישלון באמצע לא משאיר מסמך בלי הקובץ שלו.

**שם הקובץ ניתן לשינוי.** הוא מטא-דאטה של המסמך ולא של ה-blob — `DB.renameFile` נוגע ברשומת המסמך בלבד, וה-blob נשאר במקומו. `IMG_4821.jpg` אינו שם, והשם הוא מה שנוסע לדרייב ומופיע בשיתוף.

### 7.5 ייצוא ושיתוף

שלושה מסלולים בסדר יורד, ב-`js/share.js`:

| מסלול | מתי | מה מגיע |
|---|---|---|
| `navigator.share({files})` | הדפדפן תומך ומאשר את הקובץ | וואטסאפ, מייל, כל יעד שיתוף במכשיר |
| `<a download>` | אין Web Share | הורדה לדיסק |
| `window.open` | גם הקליק נחסם | כרטיסייה חדשה |

הראשון הוא היחיד שעונה על הבקשה. השניים האחרים קיימים כדי שכפתור השיתוף לא יהיה כפתור שאינו עושה דבר — יכולת שאין לה מסלול נסיגה היא יכולת שנעלמת בדפדפן הלא נכון.

**ביטול אינו כישלון.** `AbortError` מ-`navigator.share` מוחזר כ-`cancel` ואינו נופל למסלול ההורדה. משתמש שסגר את גיליון השיתוף לא ביקש קובץ בתיקיית ההורדות.

**שני דברים שונים יוצאים מכאן,** והבחירה מפורשת: הקובץ עצמו, או פרטי המסמך כטקסט. שליחת צילום של תעודת זהות אינה אותה פעולה כמו שליחת מספר פוליסה, וגיליון אחד שמציע את שניהם עדיף על כפתור שמנחש.

## 8. חיפוש — מסך ההעתקה המהירה

**אין אינדקס חיפוש.** סריקה ליניארית על כל השדות של כל המסמכים, בזיכרון.

### 8.1 התאמה

כך `84521` מוצא `84-521-03`, ו`מאזדה` מוצא את הישות.

שדה נכנס לתוצאות אם הנרמול של אחד מאלה מכיל את השאילתה:
- ערך השדה · תווית השדה · כותרת המסמך · תווית הסוג · שם הישות

**מיון:** התאמה בתחילת ערך → התאמה בתוך ערך → התאמה בתווית/כותרת/ישות. בתוך כל קבוצה, לפי `updatedAt` יורד.

### 8.2 לפני הקלדה

מסך ריק בפתיחה הוא כישלון של המסך הזה — הוא נפתח כשמישהו מחכה.

הרשימה מקומית ואינה מסונכרנת. שורה שהמסמך שלה נמחק מסוננת בזמן הרינדור, לא נמחקת מהרשימה.

## 10. הרחבות וסטיות מהאפיון המקורי

כל אחת מהן מסומנת ⚠️ בגוף המסמך. אף אחת אינה סותרת אילוץ מ-§1 באפיון.

**10.1 `multiline` על שדה.** האפיון מגדיר `fields[]` שטוח. כתובת ורשימת ילדים בספח אינן שורה אחת. הפתרון הוא **דגל ברמת השדה ולא `kind` חדש** — רישום ה-`kind` נשאר בדיוק כפי שנוקב באפיון (`id|passport|plate|policy|date|iban|phone|text`). שורה עם `multiline` גדלה לגובה התוכן; נגיעה מעתיקה את הבלוק כולו.

**10.2 `deleted` כ-`0|1`.** בוליאני אינו מפתח חוקי ב-IndexedDB. סמנטיקה זהה.

**10.3 `files[].size`.** נדרש כדי להציג את הגודל אחרי ההמרה (§5 באפיון) בלי לטעון את ה-blob.

**10.4 `confidence` נשמר ואינו מוצג.** שני סיגנלים על אותה שורה — "לאימות" מהוולידטור ו"ביטחון נמוך" מהמודל — מלמדים להתעלם משניהם. הסיגנל היחיד הוא `verified`.

**10.5 `daysLeft === 0` → `past`.** ראה §6.3.

**10.6 תזכורת ידנית משתמשת ב-`expiryDate`.** אין שדה חדש. ראה §5.1.

**מה שאינו הרחבה:** תאריכים כ-`YYYY-MM-DD`, `updatedAt` כמחרוזת ISO, היעדר אינדקס חיפוש והנרמול הגורף של תמונות — כולם החלטות מימוש בתוך מה שהאפיון מתיר.

## 11. פרסינג — שלב 4

### 11.1 הצינור

```
מסלול קלט → Files.normalize → Parse.fromMrz / Parse.fromGemini → הצעה → מסך אישור → שמירה
```

**ההצעה אינה מסמך.** היא אובייקט בזיכרון: `{ typeKey, values, expiryDate, unverified[], dropFiles, notice }`.
שום דבר ממנה לא נוגע ב-DB עד שהמשתמש לוחץ שמירה.

**גיליון ההמתנה חוסם, ולכן יש בו `דלג` — DEC-43.** שני המסלולים מציגים את אותו גיליון (`waitSheet` ב-`app.js`) ואת אותו כפתור, וסגירת הגיליון בכל דרך — הכפתור, ה-X, Escape או הרקע — היא דילוג. דילוג אינו כישלון ואינו ביטול של ההוספה: מסך המסמך נפתח מיד, הקבצים נשארים מצורפים, והשדות ממולאים ביד.

| | מה קורה בפועל |
|---|---|
| ענן (`fromGemini`) | הבקשה **נקטעת** ב-`AbortSignal`. דילוג לפני שהיא יצאה — למשל בזמן ההמרה ל-base64 — עוצר לפני השליחה |
| מכשיר (`fromMrz`) | ה-OCR אינו ניתן לקטיעה באמצע ריצה. הגיליון נסגר מיד, והתוצאה שתגיע באיחור **אינה מוצבת ואינה נוגעת בקבצים** |

הדילוג חוזר כדחייה עם `canceled: true` ולא כהצעה עם הודעת כישלון, ולכן `הפרסינג נכשל` נשאר שמור למה שבאמת נכשל.

### 11.2 MRZ

`js/mrz.js` — TD3 (דרכון, 2×44) ו-TD1 (גב תעודת זהות, 3×30).
Tesseract מתארח עצמית ב-`lib/tesseract/`, נטען עצלה, **אפס קריאות לדומיין חיצוני**.

**הפורמט קובע את הסוג, לא להפך.** TD3 → `passport`, TD1 → `id_card`, דרך `DOC_TYPES.byMrzFormat`.
המשתמש לא צריך לומר מה הוא סרק, וספרות הביקורת כבר אימתו את ההבחנה.

**המיפוי משדות ה-MRZ לשדות הטבלה יושב בטבלה** (`mrzMap`), לא בקוד. סוג חדש עם MRZ = שורה.

**מספר תעודת הזהות לא מנוחש.** הוא יושב אי-שם בשדה ה-optional data של TD1; במקום להמר על מיקום,
כל רצף ספרות שם עובר דרך ספרת הביקורת הישראלית, ומה שעובר — הוא המספר. checksum הוא ראיה טובה
ממיקום.

**כשל נושא סיבה:** `none` · `checkdigit` · `pattern` · `ocr` · `load`. נאביגו מחזירה `null` לכולם,
ו"לא זוהה MRZ" הוא הודעה אחרת לגמרי מ"זוהה ונכשל בספרת ביקורת" למי שעומד מול מסך האישור.

**תיקון מילוי, שספרת הביקורת שופטת.** תווי `<` נקראים ב-OCR כאותיות דמויות-מקל (L, K, I, C, E, X).
כשזה נוחת באזור שספרת הביקורת מחשבת עליו, קריאה תקינה נופלת שלמה. לכן כל מועמד נבדק פעמיים —
כמות שנקרא, ואז עם רצפי המילוי מוחלפים ל-`<`. **התיקון אגרסיבי ובטוח בדיוק באותה מידה: ספרת
הביקורת נשארת השופט, ותיקון שגוי פשוט לא עובר.**

**לשורת השם אין ספרת ביקורת**, ולכן שם שמגיע מ-MRZ נשמר תמיד `verified: false` — גם כשה-`kind`
שלו אינו יודע לפסול אותו. זה הדגל `unverified` בהצעה.

### 11.3 משקל, ומה זה קונה

| נכס | משקל |
|---|---|
| `tesseract.min.js` + `worker.min.js` | 0.17 MB |
| גרעין wasm (אחד מתוך שלושה, לפי הדפדפן) | 3.7 MB |
| `eng.traineddata.gz` | 2.9 MB |
| **הורדה חד-פעמית בפועל** | **6.7 MB** |

נמדד ולא נוחש: המודל השלם (10.4MB) קורא את אותו MRZ **באותה תוצאה בדיוק**, אבל פי שניים לאט יותר.
המודל הקטן נבחר על סמך המדידה.

**המסלול הוא כפתור נפרד בגיליון ההוספה**, "סריקת דרכון או ת״ז", עם המשקל כתוב עליו.
צילום רגיל של פוליסה לא גורר הורדה של 6.7MB בהפתעה.

### 11.4 הצעת ישויות

הטבלה מסמנת `peopleFrom: 'children'` על הספח. בשמירה, אם השדה מלא — עולה גיליון עם
צ׳קבוקסים, **ברירת מחדל לא מסומן**, ושתי פעולות: "שמירה" ו"שמירה בלי ליצור ישויות".
מכיוון שהטריגר הוא תוכן השדה ולא הפרסר, זה עובד גם בהזנה ידנית.


### 11.5 Gemini

**⚠️ אינו הקנון.** §6 באפיון מפנה ל-`_geminiRequest` ב-GymPro Elite, שאין אליו גישה מהסשן הזה.
`js/gemini.js` נכתב מחדש באישור מפורש, ורשום ככזה ב-`PORTED.md`. שאר האפליקציה נוגעת בו
רק דרך `Gemini.parse`, ולכן החלפה עתידית דורסת קובץ אחד.

**שתי הסכמות נפרדות, לא אחת.** שליחת מחרוזת פוליסה שהגיעה בהודעה היא ויתור אחר לגמרי
משליחת צילום של תעודת זהות. הן לא חולקות מתג, והסכמת הצילום דורשת דיאלוג אישור שאומר
במפורש מה נשלח. **בלי מפתח או בלי הסכמה — אפס בקשות יוצאות**, וזה נבדק.

**שמות מודלים לא מקודדים קשיח.** הלקוח שואל את ה-API אילו מודלים תומכים ב-`generateContent`
ומדרג אותם. קידוד שם מודל הוא תקלה עתידית מובטחת — ו"המודל העדכני" צריך להיות תוצאה
של שאילתה, לא קבוע שמישהו יזכור לעדכן.

**הדירוג — והוא הכרעה, לא נוחות:**

| # | קריטריון | הסבר |
|---|---|---|
| 1 | **שכבה** | `pro` → `flash` → `flash-lite` |
| 2 | **דור** | בתוך שכבה, המספר הגבוה קודם |
| 3 | **יציבות** | יציב לפני `preview`, בתוך אותו דור |

**השכבה גוברת על הדור**: `pro` של דור קודם קורא תעודת זהות מצולמת טוב יותר
מ-`flash-lite` של הדור הבא, והמשימה כאן היא קריאת מסמכים ולא שיחה.

**המפל רץ תמיד מלמעלה.** `429`, `5xx`, `404` (שם שהתיישן), `400` של מודל שדחה את הבקשה, **ומודל שלא ענה בזמן** — כולם מפנים מקום לבא אחריו. מה שעוצר את המפל מיד הוא **המפתח בלבד**: `403`, `401`, ו-`400` שגוגל אומרת עליו במפורש שהוא ה-API key. אין טעם לנסות שלושה מודלים עם מפתח פסול; יש כל טעם לנסות אותם כשהראשון פשוט לא ענה. DEC-44.

**שלוש תקרות זמן, לא אחת — DEC-44.**

| קבוע | על מה |
|---|---|
| `GEMINI_TIMEOUT_MS` | ניסיון בודד. חריגה = כישלון של אותו מודל, והמפל ממשיך |
| `GEMINI_TOTAL_MS` | כל הפרסינג, כולל הגילוי. חריגה = הכל נעצר |
| `GEMINI_TRIES` | כמה מודלים לכל היותר. הרשימה שגוגל מחזירה היא עשרות שמות |

מונה אחד על הכל היה נותן למודל הראשון שנתקע לבלוע את התקציב, ואז המפל **לא רץ מעולם**: המשתמש חיכה 45 שניות וקיבל כישלון בזמן ששני מודלים מהירים יותר עמדו בתור.

**רשימת המודלים נשמרת בין טעינות.** `geminiModelsSeen` הוא קאש של הגילוי האחרון. פרסינג בטעינה חדשה משתמש בו ומתחיל מיד בבקשה למסמך, והרענון קורה **אחרי**, פעם אחת בטעינה, ב-`setTimeout` שאינו מתחרה על הרוחב פס דווקא כשהמשתמש מחכה. עד DEC-44 כל טעינה שילמה סיבוב רשת שלם לפני שבייט אחד של המסמך יצא.

**מה שנשלח קטן ממה שנשמר.** `Files.forParse` מקטין לצלע `GEMINI_EDGE` ומקודד ב-`GEMINI_QUALITY` — עותק שחי עד סוף הבקשה, והמקור בכספת אינו נוגע. גוגל מרצפת תמונה ל-768px לפני שהיא קוראת אותה, ולכן הפיקסלים העודפים אינם קונים דיוק אלא שניות של העלאה, שהן רוב ההמתנה במכשיר סלולרי. מעל `GEMINI_MAX_BYTES` נעצרים לפני השליחה: בקשה של עשרות מגה-בייט אינה נכשלת מהר, היא נכשלת אחרי דקה.

**"התשובה חזרה ריקה" פוצל לשלושה.** `finishReason` מבדיל בין מודל שסירב לקרוא את המסמך (`SAFETY` — קורה דווקא על תעודות זהות), תשובה שנקטעה באורך (`MAX_TOKENS`), ותשובה ריקה באמת. מי שקורא "ריקה" מנסה שוב ושוב; מי שקורא "סירב" ממלא ידנית.

**המודל שהצליח אינו מוקפץ לראש.** `geminiLastModel` נכתב לתצוגה בלבד. הקפצה נשמעת
כאופטימיזציה עד ש-`429` חד-פעמי על מודל חלש נועל אותו בראש לכל הקריאות הבאות — כלומר
הופכת את הסדר שנבחר להמלצה. המחיר הוא קריאה כושלת אחת כשהראשון עמוס.

**המפל ניתן להגדרה.** `geminiModels` — רשימה מסודרת שהמשתמש עורך בהגדרות, מודל בכל
שורה. כשהיא לא ריקה היא **גוברת על הדירוג ואינה שואלת את ה-API בכלל**: זה הסדר שלו,
כולל מודל שאינו ברשימת הגילוי. כפתור "גילוי המודלים הקיימים" שואל את ה-API בלי קאש
וממלא את הרשימה מדורגת — כך "המודל העדכני" הוא פעולה שהמשתמש עושה, ולא הבטחה.

**הפרומפט נבנה מהטבלה** (`Gemini.schemaText`). אין בקובץ רשימת שדות משלו; סוג מסמך חדש
הוא שורה, והפרומפט גדל איתה. `temperature: 0.1`, `responseMimeType: 'application/json'`.

**מה שחוזר עובר סינון:** שדה שאינו קיים בשורת הסוג נזרק, כל ערך עובר `canonical` של ה-`kind`
שלו, ותאריך שאינו קיים בלוח נדחה.

**תיקון סדר ספרות בת״ז, שספרת הביקורת שופטת.** ספרת הביקורת של תעודת זהות היא
**האחרונה**, ומודל שקורא מסמך בעברית מעביר אותה לפעמים לראש המספר — סדר שנראה סביר
לעין ושגוי לחלוטין. `KINDS.id.repair` מסובב את הספרה הראשונה לסוף ומקבל את התוצאה
**רק אם המסובב עובר את ספרת הביקורת בעוד המקורי נכשל**. אותה לוגיקה בדיוק כמו תיקון
המילוי ב-MRZ (§11.2): התיקון מותר להיות אגרסיבי כי הבדיקה נשארת השופט.

שני סייגים:
- **חל על ערכים שמכונה הפיקה בלבד.** הזנה ידנית שגויה היא שגיאת הקלדה, וסיבוב שלה
  היה הופך טעות אחת למספר תקין **אחר** — גרוע יותר מלהשאיר אותה שגויה.
- **שדה שתוקן נשמר מסומן "לאימות"**, וההודעה במסך האישור אומרת במפורש שסדר ספרות
  תוקן. תיקון שקט הוא בדיוק מה ש-§6 אוסר.

הפרומפט גם אומר למודל מפורשות שהמספר הוא תשע ספרות, שספרת הביקורת אחרונה, ושאפס חסר
מתווסף בהתחלה ולעולם לא בסוף. שני הדברים יחד — לא אחד מהם. הפלט הולך לאותו מסך אישור ולאותם ולידטורים כמו הזנה ידנית —
**פלט של מודל אינו נאמן יותר מפלט של OCR.**

### 11.6 פענוח לפי דרישה

הפרסינג האוטומטי רץ **פעם אחת**, ורק כשהוא כבר מוגדר בזמן ההעלאה. בלי כפתור, מסמך
שלא זוהה — או שהמפתח הוגדר רק אחר כך — נשאר להזנה ידנית בלי שום דרך לנסות שוב.
**יכולת שאין לה כפתור היא יכולת שאינה קיימת.**

לכן במסך המסמך יש **"פענוח אוטומטי"**, שמופיע בכל פעם שיש קובץ — גם בעריכת מסמך קיים.

- **ממלא רק שדות ריקים.** מי שכבר הקליד משהו לא מאבד אותו לטובת ניחוש של מודל.
- **לא מוגדר → מסביר מה חסר ולוקח להגדרות**, במקום כפתור שלא עושה כלום.
- **סוג שאינו מתאים לישות** — ביטוח רכב על אדם — מוחזר כהודעה מפורשת ולא נבלע.
  זה היה באג: הטופס נפל בשקט לסוג אחר וההודעה אמרה "שדות מולאו" בזמן ששום שדה לא מולא.
  שני המסלולים, האוטומטי ולפי דרישה, עוברים היום דרך אותה הודעה.
- ג׳מיני מקבל גם PDF ולא רק תמונה. MRZ עדיין צריך תמונה.

**מה שלא נעשה:** שדות שג׳מיני מילא ואין להם ולידטור אינם מסומנים "לאימות" אוטומטית.
מסך האישור קיים כדי שאדם יבדוק, והלחיצה על שמירה **היא** האימות. החריג היחיד הוא שם מ-MRZ,
שנשאר מסומן כי OCR משבש שמות בדרכים שנראות סבירות. האסימטריה מכוונת ומתועדת.

## 12. דרייב וסנכרון — שלב 5

### 12.1 הרשאות

`drive.file` + `drive.appdata`. §8 באפיון קבע `drive.file` **בלבד**, וזו סטייה מאושרת (DEC-16).

**למה:** `drive.file` רואה רק קבצים שהאפליקציה עצמה יצרה. מחיקת נתוני אתר מוחקת את מזהה
התיקייה, והתיקייה נשארת בדרייב **בלתי נראית** — האפליקציה תיצור חדשה ושני המכשירים
יתפלגו בשקט. `drive.appdata` נותן גישה **רק לתיקייה נסתרת של האפליקציה עצמה**, ושם יושב
קובץ אחד: `folder.json` עם מזהה התיקייה. הוא חי בחשבון ולא בדפדפן.

יש בדיקה שמוחקת את המזהה המקומי ומוודאת שהתיקייה נמצאת מחדש ולא נוצרת שנייה.

**הטוקן חי בזיכרון בלבד.** טוקן גישה ב-IndexedDB הוא התחייבות, לא נוחות.

### 12.7 גשר Apps Script — התחבורה שאינה מבקשת התחברות

`js/bridge.js` + `tools/bridge.gs`. **ברירת המחדל** (DEC-31), ו-OAuth נשאר כחלופה.

הגשר הוא web app של Apps Script שרץ **בחשבון של המשתמש**. הדפדפן שולח POST עם סוד משותף, והגשר עושה את העבודה מול Drive. אין OAuth, אין פופאפ, ואין טוקן שפג — מדביקים כתובת וסוד פעם אחת.

**אותו חוזה תחבורה בדיוק** — `connected · getDb · putDb · uploadBlob · downloadBlob` — ולכן `Sync` אינו יודע מי משרת אותו, וההחלפה היא `App.transport()`.

**`fetch` בלי כותרות, וזה לא שכחה.** גוף מחרוזת בלי `Content-Type` מפורש נשלח כ-`text/plain`, ערך מותר ב-CORS, ולכן הבקשה "פשוטה" ואין preflight. `Content-Type: application/json` מפעיל `OPTIONS`, ו-Apps Script אינו עונה עליו.

**הגשר נוגע בתיקייה אחת.** כל הורדה מאמתת שהקובץ יושב בתוך `DocVault`; אין פעולת מחיקה; אין כתיבה מחוץ לתיקייה. זו הקשחה מכוונת מול נאביגו, שאצלה `download` על מזהה שרירותי מחזיר כל קובץ בחשבון.

**התיקייה מסומנת ב-`description`** (`family-vault-root`) ונמצאת מחדש בלי מזהה שמור — מה ש-`appDataFolder` עושה עבור OAuth.

**תקרת גודל:** `CONFIG.BRIDGE_MAX_BYTES`. אין resumable, והכל base64 בגוף JSON.

### 12.8 קובץ המפתחות — מכשיר שני בלי הקלדה

`js/keyfile.js`. DEC-42.

מכשיר שני מתחיל ריק, ומה שמפריד בינו לבין אפליקציה מלאה הוא ארבע מחרוזות שאי אפשר לנחש ואי אפשר להקליד בלי טעות. הקובץ נושא אותן, וזה **כל** תפקידו: **הוא אינו נושא נתונים.** הכספת מגיעה מהסנכרון הראשון, שהמפתחות הם מה שמאפשר אותו.

**הטבלה היא המקור.** `CONFIG.KEYFILE.FIELDS` קובעת מה נכתב לקובץ, מה מוצג לפני האישור ומה נכתב ל-`settings` — ולכן **מפתח נייד נוסף הוא שורה בטבלה ואפס קוד חדש**, בדיוק כמו סוג מסמך ב-`DOC_TYPES`.

| עמודה | מה היא עושה |
|---|---|
| `key` | מפתח ב-`settings` (§3.5) |
| `label` | מה שמוצג במסך האישור |
| `type` | `text` · `list` · `enum` — הטיפוס שנאכף בשני הכיוונים |
| `options` | לערכי `enum`: המפתח והתווית |
| `secret` | הערך ממוסך בתצוגה (`KINDS.mask`) |
| `pref` | העדפה ולא מפתח — נוסעת, אך אינה מצדיקה קובץ בפני עצמה |

**שש השורות של v1:** `backupMode` (pref) · `bridgeUrl` · `bridgeToken` (secret) · `driveClientId` · `geminiKey` (secret) · `geminiModels` (pref).

**מבנה הקובץ:**

```json
{ "app": "family-vault", "kind": "keys", "format": 1,
  "created": 1756100000000,
  "keys": { "backupMode": "bridge", "bridgeUrl": "…/exec", "bridgeToken": "…" } }
```

**מה אינו נוסע, ובכוונה:** `pinHash` — שער של מכשיר ולא של חשבון. שלוש ההסכמות לשליחה לגוגל — אישור אישי; ייבוא שמדליק אותן בשקט שולח צילומי תעודות זהות בלי שאיש אמר "כן". `driveFolderId` ו-`driveDbFileId` — קאש של מצביעים בחשבון אחר, ומצביע שגוי גרוע ממצביע חסר.

**אותה ולידציה בשני הכיוונים.** `clean()` רצה גם בייצוא וגם בייבוא, ולכן ערך מטיפוס שגוי — קובץ שנערך ביד, או גרסה עתידית — נזרק בגבול ולא נכנס ל-`settings`. `bridgeUrl` שהוא מספר נשבר בקריאה הבאה לגשר, רחוק מאוד מהמקום שבו הוא נכנס. הקריאה היא **לפי הטבלה ולא לפי הקובץ**: מפתח שאיננו מכירים אינו נכתב.

**הטעינה ממזגת.** קובץ שנושא רק מפתח Gemini לא ימחק גשר מוגדר, והכתיבה סדרתית — ייבוא שנקטע משאיר הגדרות שלמות ולא חצי הגדרה. מיד אחריה `Sync.transport` מוחלף ומחזור סנכרון רץ, ולכן הכספת יורדת בלי פעולה נוספת.

**האזהרה היא חלק מהתכונה.** הקובץ נושא את הסוד בגלוי — הצפנתו הייתה מחייבת סיסמה שנייה בערוץ אחר, כלומר בדיוק את ההקלדה שהתכונה באה למחוק. לכן הייצוא עובר במסך אישור שאומר מה יש בקובץ ומה המשמעות, והמיסוך בייבוא מאפשר לוודא שזה הקובץ הנכון בלי לקרוא אותו מעל הכתף.

### 12.2 מבנה בדרייב

```
DocVault/
  docvault-db.json
  files/
    <docId>__<שם הקובץ>
```

תיקייה שטוחה אחת (DEC-15). ההעלאה היא `multipart/related` שנבנה ידנית.

### 12.3 מה עוזב את המכשיר ומה לא

| נשלח | לא נשלח |
|---|---|
| `entities` במלואן | `settings` — כולל מפתח Gemini ו-hash ה-PIN |
| `docs` — שדות, תאריכים, מטא של קבצים | `blobs` — הם נשלחים כקבצים נפרדים, לא בתוך ה-JSON |
| `driveFileId` של כל קובץ | **`blobId`** — מזהה מקומי, נחתך בגבול הייצוא |
| תפוגת הדרכון | **שדות הדרכון** — `syncFields:false` (DEC-13) |

### 12.4 המיזוג

ported from Navigo: `js/db.js:mergeSync`. ברמת הרשומה, `updatedAt` גדול יותר מנצח,
tombstones חיים לנצח, ותיקו נשאר תיקו — המקומי מנצח בשקט ואין שדה שובר.

**החריג היחיד הוא `files[]`, והוא קריטי.** אצל נאביגו ה-blob יושב על הרשומה ויש לו הצלה
בשורה אחת. אצלנו הוא בחנות נפרדת, ודריסה ברמת הרשומה הייתה מותירה מסמך שמצביע לשום מקום
בזמן שהקובץ שלו שוכב בדיסק. לכן:

- קובץ שכבר עלה מזוהה לפי `driveFileId`, וה-`blobId` המקומי שלו נשמר.
- קובץ מקומי **שטרם עלה** אינו קיים בצד המרוחק — והוא שורד את המיזוג. בלי זה, סנכרון
  שרץ לפני ההעלאה מוחק את הקובץ מהמסמך.
- קובץ ממכשיר אחר נכנס עם `blobId: null` ומורד בשלב הבא.

### 12.5 המחזור

```
getDb → merge → העלאת blobs שטרם עלו → הורדת blobs חסרים → putDb (אם צריך)
```

**מנעול `_syncing`.** בלי זה שתי הרצות משתלבות ואחת דורסת את השנייה; נאביגו מדווחת שזה
כבר קרה להן.

**התור אינו מקור האמת — ה-DB המקומי הוא.** `Sync.queue()` הוא `setTimeout` בודד של
4 שניות. סגירת האפליקציה לפני שהוא רץ **דוחה את הדחיפה ולא מאבדת אותה**: הכתיבה כבר
בוצעה, וההרצה הבאה מגלה שהמקומי חדש יותר.

**טריגרים:** עלייה · `visibilitychange` · `online` · כל כתיבה ל-DB דרך הוו `DB.onWrite`.
הוו קיים כדי ששכבת האחסון תישאר בורה מסנכרון ובכל זאת שאף מסלול כתיבה לא יוכל לשכוח.

**אין retry ואין backoff.** ההרצה הבאה היא ה-retry. על רשת מקרטעת, backoff ברקע מייצר
סדרת קריאות שכולן ייכשלו ומרוקן סוללה, בזמן שהמשתמש ממילא יחזור לאפליקציה.

### 12.6 מה שלא נבדק

התחבורה נבדקת מול Google API מזויף, והמיזוג מול **שני דפדפנים אמיתיים** עם שני
IndexedDB נפרדים שחולקים דרייב מזויף. **סבב אמיתי מול גוגל לא נבדק** — אין חשבון בסביבה.
`DEBT.md` D8.

## 13. PWA, אופליין ומנגנון הגרסה — שלב 6

### 13.1 מה נשמר מראש ומה לא

| נכס | precache | למה |
|---|---|---|
| מעטפת: HTML, CSS, 17 מודולי JS | כן | ~200KB |
| Assistant, שני תת-סטים | כן | 29KB |
| אייקונים | כן | 44KB |
| pdf.js + worker | כן | 1.4MB |
| **`standard_fonts/` — 14 קבצים** | **כן** | ~800KB |
| `lib/tesseract/` | **לא** | 6.7MB, ורוב המשתמשים לא יסרקו דרכון אף פעם |
| `lib/pdfjs/cmaps/` | **לא** | 1.7MB, רלוונטי ל-PDF בסינית או יפנית בלבד |

**גופני התחליף חייבים precache מפורש.** הם נטענים **עצלה** מתוך pdf.js, ולכן runtime
caching אינו תופס אותם — מסמך ייפתח אופליין עם אותיות חסרות, והבאג ייראה כמו PDF פגום
ולא כמו קובץ חסר. זו אזהרה מפורשת שהגיעה מנאביגו, ויש עליה בדיקה שסופרת 14.

הכל מ-precache ≈ **2.5MB**. מה שלא — נתפס ב-runtime cache בשימוש הראשון.

### 13.2 המנגנון המשולש

| נקודה | תפקיד |
|---|---|
| `CACHE_VERSION` ב-`sw.js` | מייצר `CACHE_NAME` חדש ומפרק את הקאש הישן ב-`activate` |
| `version.json` | מה שהשרת מכריז. נטען `no-store`, מקור האמת |
| `_BUNDLE_VERSION` ב-`index.html` | מה שרץ עכשיו בדפדפן, להשוואה |

שלוש הנקודות **נחוצות** — הן ממלאות שלושה תפקידים שונים. מה ששבור הוא לכתוב את המספר
ידנית בשלושתן. זו בעיית סנכרון, לא בעיית ארכיטקטורה, וסנכרון ידני נשכח.

לכן: **`node tools/bump.mjs`** קורא את `version.json` וכותב את השתיים האחרות,
ו-**`tests/pwa.mjs` נכשל אם הן נפרדו**. נאביגו המליצה: "אם אתה עושה רק דבר אחד — עשה את הבדיקה".
עשינו את שניהם. `CONFIG.VERSION` קורא את `_BUNDLE_VERSION` ולא מכפיל אותו לנקודה רביעית.

### 13.3 שלוש שכבות ההגנה על העדכון

ported from Navigo — כולן נכתבו נגד באגים אמיתיים של ספארי מול GitHub Pages, ואנחנו מוגשים מאותו מקום:

1. רישום עם `updateViaCache: 'none'` — בלי HTTP cache לסקריפט ה-SW עצמו.
2. `version.json` חדש וה-SW לא מתעדכן → רישום מחדש עם `./sw.js?v=<גרסה>`, כתובת שאף קאש
   לא יכול להגיש ממנה עותק ישן.
3. `install` מושך כל קובץ עם `cache: 'no-cache'` — למלא מהשרת, לא מקאש HTTP מיושן.

**`IndexedDB` לא נמחק באף אחת מהן.** סכמת ה-DB מנוהלת בנפרד דרך `onupgradeneeded`.

**רענון רק בעדכון אמיתי.** בטעינה הראשונה אין `controller`, וה-SW תופס שליטה מיד;
רענון שם הוא הבהוב מיותר בפתיחה הראשונה. מרעננים רק כשהוחלף controller שכבר היה.
זה באג שנתפס בבדיקה, לא בקריאת קוד.

### 13.4 צופה ה-PDF

ported from Navigo: `js/ui.js:renderPdf`. **`<canvas>` ולא `<iframe>`** — `blob:` ב-iframe
אינו אמין ב-iOS Safari, ו-`<embed>` מציג צופה מערכתי שאין עליו שליטה.

**`ctx.direction = 'ltr'` היא השורה שמצדיקה את כל פרוטוקול §14.** ההקשר יורש RTL מה-DOM,
`fillText` מתעגן לצד ההפוך, ו-clip rects של ה-PDF חותכים אותיות. הסימפטום נראה כמו PDF פגום
ולא כמו באג RTL — שעות של חיפוש במקום הלא נכון, שנחסכו בשורה אחת שהגיעה מסשן אחר.

**כל `blob:` URL נרשם ומבוטל בסגירה.** אצל נאביגו זו דליפה מוכרת שהם אמרו במפורש לא לפורט.

## 14. העוזר — שלב 7

שיחה בעברית שרואה את הכספת ויכולה להציע בה שינויים. `js/chat.js`.

**אופציונלי לגמרי.** דורש מפתח Gemini והסכמה שלישית ונפרדת — `geminiConsentChat`. בלעדיו המסך מסביר מה חסר ומפנה להגדרות, ושאר האפליקציה אינה מושפעת.

### 14.1 שני חצאים, וגבול ביניהם

```
Chat.context + Chat.prompt  →  Gemini.chat  →  Chat.compile  →  אישור במסך  →  Chat.apply
                                                   ↑
                                          הגבול. פונקציה טהורה.
```

`Chat.compile` היא היחידה שמחליטה מה מותר. היא **טהורה** — מקבלת פעולות ומצב, מחזירה פעולות מאומתות ורשימת שגיאות, ולא נוגעת ב-DB. שום דבר שהמודל אמר אינו נכתב לפניה, ושום דבר שהיא פסלה אינו נכתב אחריה.

מה שהיא בודקת: המזהה קיים · המפתח קיים בסוג המסמך · הסוג מתאים לסוג הישות · שדה חובה אינו מרוקן · התאריך קיים בלוח השנה · הערך מנורמל ע"י ה-`kind` ומאומת בוולידטור שלו.

`verified` נקבע כאן בדיוק כמו ב-`Forms.doc.read`: נכון אם ורק אם עבר את הוולידטור. ערך שנכשל **נשמר ומסומן**, ולא נזרק — אותו כלל שחל על MRZ ועל Gemini (§10).

### 14.2 האישור

כל פעולה מוצגת ככרטיס עם תיאור בעברית, ורק כפתור "החלה" כותב. זה אותו כלל של מסך האישור, על ערוץ אחר: **פלט מודל אינו נשמר בשקט.**

**הערך הקודם מוצג לצד החדש** — "עכשיו: X" מתחת לתיאור, מפורמט לפי ה-`kind` של השדה. ההבדל בין "עדכון תאריך" לבין "עכשיו 12/08" הוא ההבדל בין אישור אוטומטי לבדיקה.

**מסומן כברירת מחדל רק מה שבטוח.** `Chat.SAFE` — `setField`, `setDate`, `setTitle`, `setNotes`, `createEntity`, `createDoc`. `clearField`, `moveDoc` ו-`renameEntity` מגיעים לא מסומנים: סימון-כברירת-מחדל הוא הצהרה "זה בטוח והפיך", והיא אינה נכונה לכולן.

**התוצאה חוזרת למודל** כתור (`Chat.outcomeText`) — מה הוחל ומה נדחה. מודל שאינו יודע שדחו אותו מציע שוב את אותו דבר; מודל שכן יודע מציע חלופה.

### 14.3 גודל ההקשר, וצמצום לפי זמן

**שולחים הכל, ומעולם לא לפי השאלה.** סינון לפי השאלה הוא בדיוק המנגנון שמסתיר את מה שנשאלו עליו: "מה עם ההוא מהפעם הקודמת" אינו נותן מילת מפתח, ומערכת שמסננת לפי דמיון תחזיר הקשר ריק ותגרום למודל לענות "אין לי מידע" על מידע שיש לו.

**הצמצום הוא לפי זמן:** מסמך שפג לפני יותר מ-`Chat.STALE_DAYS` (שנה) מצטמצם לשורה — מזהה, ישות, סוג, כותרת ותפוגה, בלי שדות ובלי הערות. דטרמיניסטי, ניתן להסבר, ואינו תלוי בניסוח.

**מספרים מגיעים מחושבים:** `daysLeft` לכל מסמך ו-`counts` לפי סוג. מודל שמחשב טועה בשקט, וכל מספר שהמשתמש עשוי לצטט עדיף שיגיע מוכן.

`Chat.contextSize` מוצג במסך השיחה. מדידה שקיימת רק בקונסול היא מדידה שאיש לא רואה.

### 14.4 מה עוזב את המכשיר

`Chat.context` עובר דרך `DB.forSync`, ולכן **DEC-13 חל גם כאן**: שדות הדרכון אינם נשלחים. הדרכון עצמו מופיע ברשימה כדי שהעוזר לא יניח שהוא ריק, בלי הערכים שלו.

גרסאות שנדחקו אינן נשלחות (§6.6) — העוזר עובד על העדכני, כמו כל מסך אחר.

זו ההסכמה הרחבה מבין השלוש: לא מסמך בודד אלא מפת הכספת, בכל הודעה. הדיאלוג אומר זאת במילים.

### 14.5 הפרומפט נבנה מהטבלה

רשימת השדות מגיעה מ-`Gemini.schemaText()`, ורשימת סוגי הישות מ-`CONFIG.ENTITY_TYPES`. סוג מסמך חדש הוא שורה בטבלה, והעוזר יודע עליו באותו רגע.

## 15. קנה מידה — האפליקציה נעולה, המסמך לא

מסך שגדל וקטן בטעות בזמן שגוררים ישות או לוחצים על שורה הופך כל מחווה למפוקפקת. הנימוק אינו אסתטי: המשתמש מפסיק לסמוך על מה שהאצבע שלו עושה.

**האפליקציה:** `meta viewport` עם `user-scalable=no, maximum-scale=1, minimum-scale=1`. ספארי מתעלם מזה מאז iOS 10, ולכן `js/app.js:Zoom` חוסם גם את שלוש המחוות — `gesture*`, `ctrl+wheel`, והקשה כפולה. בחזרה לאפליקציה קנה המידה נאכף מחדש בכתיבה מחדש של ה-`meta`.

**המסמך:** `UI.zoomable` בצופה. צביטה, הקשה כפולה, וכפתורים. כל החסימות למעלה נעצרות בגבול `.zoom-stage` — יכולת שהוסרה מהאפליקציה חייבת לחיות איפשהו, ובמסמך היא באמת נחוצה.

**הזום משנה רוחב ולא `transform`.** ל-`transform` אין השפעה על הפריסה, ולכן גלילה לתוך תמונה מוגדלת הייתה דורשת ריפוד מחושב; שינוי רוחב מגדיל את התוכן באמת, והגלילה של הדפדפן מטפלת בהזזה בחינם.

**`object-position: 50% 0` על העוגן** היא ברירת המחדל, לא התשובה. תעודת זהות עם ספח מצולמת כמלבן גבוה, ומרכזו הוא הספח — כלומר בדיוק החלק שאינו התעודה. אבל "ראש התמונה" הוא ניחוש טוב ולא נכון תמיד: בצילום עם שוליים למעלה הוא מציג שולחן.

**לכן המסגרת נבחרת ביד, בטופס העריכה.** `UI.cropper` — גרירה על התצוגה עצמה, מחוון מיקום, מחוון הגדלה, צביטה בשתי אצבעות, גלגלת במחשב, וחיצים ופלוס־מינוס במקלדת. כולם כותבים את `files[0].focusX/focusY/focusZ`.

**המסגרת מצוירת בגאומטריה מפורשת, לא ב-`object-fit`** (DEC-46). `UI.applyFocus` ממקמת את התמונה `absolute` בגודל `נטו · cover · z`, באחוזים מהאב. מעל 1 היא נחתכת, מתחת ל-1 היא נראית כולה על הרקע. `object-fit: cover` אינו יכול לשמש כאן: הוא חותך בזמן הפריסה, ו-`transform` שמוקטן אחריו מקטין את החיתוך במקום לגלות אותו — כלומר מאפשר להתקרב ולא להתרחק.

**האחוזים אינם קישוט.** היחס בין התמונה למסגרת תלוי רק ביחסי הצורה של שתיהן, ולכן המסגרת שורדת סיבוב מסך בלי מאזין `resize`.

כל אתר ציור חייב אב עם `position: relative` ו-`overflow: hidden`. `object-position` עדיין נכתב באופן סינכרוני, כדי שהפריים שלפני טעינת התמונה יהיה מכוון נכון.

**הרצפה נגזרת מהתמונה:** `contain / cover` — ההקטנה שבה כולה נכנסת למסגרת בדיוק. `CROP_MIN_ZOOM` הוא רצפת בטיחות לערך שנשמר בלבד.

**הסרך נגזר מחדש בכל שינוי גודל:** `נטו · cover · z − מסגרת`. מכאן שני דברים — הגרירה מתחלקת בו כדי לעקוב אחרי האצבע, וציר שלא היה בו מה להזיז נעשה חי.

הגרירה מומרת **לפי הסרך האמיתי בפיקסלים** (גובה התמונה כשהיא נמתחת לרוחב המסגרת, פחות גובה המסגרת), ולכן היא 1:1 ולא "בערך". כשהתמונה **רחבה** מהמסגרת, `cover` חותך לרוחב ואין סרך אנכי כלל — הבורר מושבת ואומר למה, במקום להזיז ולא לעשות דבר.

הבורר מכוון ל-`files[0]` בדיוק, ולא לקובץ הראשון שהוא תמונה: העוגן מצייר את `files[0]`, ובורר שהיה מכוון לקובץ אחר היה מזיז מסגרת שאיש לא רואה. ל-PDF אין בורר — העוגן שלו הוא עמוד ראשון מרונדר, לא חלון לתוך תמונה.

## 16. מסך הבית וסידור ידני

### 16.0 מה שנכנס לעיגול — DEC-41

`Files.avatar` שומרת את התמונה שלמה ומקטינה לפי הצלע הקצרה, והתצוגה חותכת עיגול
מהמרכז. בתצלום רחב — רכב, בית — **הרוחב הוא הנושא**, וחיתוך כזה מותיר ידית דלת.

לכן תמונה רחבה מ-`AVATAR_WIDE_RATIO` (1.5) מרופדת לריבוע **בייבוא**: קנבס בצלע
`min(רוחב המקור, AVATAR_SQUARE_EDGE)`, צבע רקע שנדגם מטבעת הפיקסלים בשולי התצלום,
והתמונה במרכז ב-92% מהצלע. הריפוד בייבוא ולא בתצוגה, כדי שמסלול הרינדור יישאר אחד:
אותו `object-fit: cover`, אותו `avatarFocus`, ואותו בורר מסגרת — שמזהה ריבוע בעיגול
ואומר מעצמו "אין מה להזיז".

רק רחבה, לא גם גבוהה: תצלום אנכי הוא כמעט תמיד של אדם, והריבוע שנחתך ממרכזו הוא הפנים.

### 16.1 הפריסה נגזרת מהתמונה — DEC-39

לישות יש `avatarImage` (§3.2), ולכן **התמונה היא הנתון החזק ביותר במסך ומה שקובע את
הפריסה.** לתמונה של אדם ולתמונה של בית מגיעה מסגרת אחרת: פנים מזוהות בעיגול, ורכב או
דירה בפס רחב.

`CONFIG.ENTITY_GROUPS` הוא שקובע מי מוצג איך, ו-`group` הוא עמודה ב-`ENTITY_TYPES`:

| קבוצה | פריסה | מי | האריח |
|---|---|---|---|
| `people` | `rail` | `person` | דיוקן 64px ברצועה שנגללת לצדדים |
| `assets` | `board` | `vehicle` · `home` · `other` | פס תמונה 16:10, שני אריחים בשורה |

**לקבוצה אין תווית משלה.** התווית נבנית משמות הסוגים שיש להם ישויות **בפועל**, ולכן
משפחה בלי רכב רואה "בית" ולא "רכב ובית". `screens.js` אינו מזכיר שם של סוג ישות.

**המצב על האריח, לא המנייה.** `Expiry.next` מחזירה את התפוגה הקרובה של הישות, ומה
שמוצג הוא היא ולא "3 מסמכים". הקשת החמה נשארת של מנוע התפוגה: ישות רגועה נשארת אפורה
לגמרי (DEC-05), וישות שדורשת מבט מקבלת **טבעת בצבע הדלי** סביב התמונה ואת אותו צ׳יפ.
`Expiry.shortLabel` היא התווית שנכנסת לאריח בן 106 פיקסלים; `Expiry.label` נשאר הקנון
בכל מקום אחר.

### 16.2 המסד

הסימן (DEC-40), שם האפליקציה, ושורת מצב: `N מסמכים · אחד דורש טיפול`. החלק השני מופיע
רק כשיש מה לומר, והוא לחיץ אל רשימת התפוגות. זה מה שמחליף את הבאנר היומי במסך הזה.

**האקסנט מקבל תפקיד בראש המסך.** עד DEC-39 הוא הופיע פעמיים בלבד, ושתיהן בתחתית.
עכשיו: אריח הסימן, שני ענני הגוון בשדה העליון, מוני הקבוצות, הכרית תחת הטאב הפעיל
והזוהר של כפתור ההוספה. `--tint-1/2` ו-`--glow` נגזרים מהאקסנט ואינם צבע רביעי —
אותו גוון בשקיפות. שקיפות אמיתית בשלושה מקומות: אריחי הרצועה, הסרגל התחתון שהתוכן
נגלל מתחתיו, ותווית הסוג שעל התמונה.

### 16.3 סידור ידני

**ישויות: קיבוץ לפי `ENTITY_GROUPS`, ובתוך קבוצה לפי סדר `ENTITY_TYPES`** — אדם ראשון. זו שורה בטבלה, לא סדר שכתוב במסך. בתוך קבוצה: `sortOrder`, וברירת המחדל היא סדר היצירה.

**מסמכים בתוך ישות: `sortOrder` גם כן**, וברירת המחדל היא האחרון שנגעו בו (`updatedAt` יורד). `Screens.docOrder` מיישמת בדיוק את זה — `sortOrder` כשיש, ואחרת החותמת — כך שמי שלא גרר מעולם רואה מה שראה תמיד.

**גרירה בלחיצה ארוכה כותבת `sortOrder` לכל הרשימה** במרווחים של 1000. אחרי גרירה אחת הכל מפורש, ואין ערבוב בין נגררים ללא-נגררים. הדריסה קבועה: היא שורדת רענון וסנכרון, כי `sortOrder` יושב על הרשומה — וגם עריכה, כי `Forms.doc.read` מעביר אותו במפורש לאובייקט החדש שהוא בונה.

### 16.4 שלושה דברים שבלעדיהם הגרירה לא עובדת בנייד

זה עבד בעכבר ונכשל במכשיר, וכל אחד מהשלושה הוא כשל בפני עצמו:

1. **`touch-action` נקבע בתחילת המחווה, לא באמצעה.** הוספת `.reordering` אחרי 320ms מגיעה מאוחר מדי — הדפדפן כבר החליט שהמגע עשוי לגלול. מה שכן עוצר אותו הוא מאזין `touchmove` **לא פסיבי** עם `preventDefault`, והוא עובד כאן דווקא מפני שהלחיצה הארוכה קודמת: בזמן ההמתנה האצבע לא זזה, גלילה עוד לא התחילה, והביטול הראשון מונע אותה מלהתחיל.
2. **iOS מקפיץ בועת בחירה על לחיצה ארוכה** ומבטל את רצף המצביע. `-webkit-touch-callout: none` ו-`user-select: none` על הכרטיסים סוגרים את זה.
3. **גלילה אוטומטית בקצוות.** בלעדיה אי אפשר לגרור אל מחוץ למסך, וברשימה ארוכה מהמסך זה חצי מהמקרים. `UI.reorder` מוצאת את האב הגליל הקרוב, ואם אין — מגלגלת את החלון.

**הציר מגיע מהקורא.** `UI.reorder` מקבלת `axis`: `'y'` לרשימה, `'x'` לרצועה, `'grid'`
ללוח. הבדיקה "לפני מי" נגזרת ממנו ומכיוון הכתיבה — ב-RTL "מוקדם יותר" הוא X **גדול**
יותר, ובלוח השורה גוברת על הטור. ההזזה שנושאת את הכרטיס פועלת רק בציר המחווה: כרטיס
ברשימה אנכית שנגרר גם הצידה נראה כאילו הוא נשמט מהיד. ומיכל רשאי להחזיק ילדים שאינם
פריטים — בסוף הרצועה יושב "ישות חדשה" — ולכן הסוף נמדד מול הפריט האחרון ולא מול הילד
האחרון.

**לחיצה ארוכה ולא גרירה מיידית**, כדי שגלילה של רשימה לא תיהפך בטעות לגרירה. אחרי גרירה נבלע קליק אחד — אחרת שחרור על כרטיס היה מנווט אליו — והדגל מתאפס גם בהרפיה, כי בנייד לא תמיד מגיע קליק אחרי גרירה.

## 17. אווטאר של ישות

תמונה נשמרת כ-**data URL על רשומת הישות**, לא כ-blob נפרד. שלוש סיבות, וכולן מכריעות:
היא נצבעת בפריים הראשון בלי קריאה אסינכרונית שמהבהבת · היא מסתנכרנת לדרייב עם הישות בלי שורת קוד בסנכרון · והיא נוסעת עם ה-tombstone הנכון במחיקה.

**התמונה נשמרת שלמה ואינה נחתכת בבחירה.** מה שנקבע הוא הצלע הקצרה — 256px — כך שכל חיתוך ריבועי אפשרי יוצא לפחות בגודל הזה. JPEG, והאיכות יורדת בלולאה עד שהתוצאה נכנסת מתחת ל-120KB.

**החיתוך לעיגול הוא `object-fit: cover` בזמן תצוגה**, עם `object-position` מתוך `avatarFocus` — ולכן אפשר להזיז את המסגרת גם חודש אחרי הבחירה, בלי לבקש קובץ מקורי שכבר אין. חיתוך מהמרכז בזמן הבחירה היה מקבע ניחוש שאי אפשר לתקן.

`avatarFocus` הוא `{ x, y }` באחוזים, ברירת מחדל `{ 50, 50 }` — בדיוק מה שאווטאר שנשמר לפני שהבורר היה קיים כבר נראה, ולכן הוא אינו משתנה.

הבורר בטופס הישות הוא `UI.cropper` בצורת עיגול, **בלי מחוון**: בעיגול הסרך יכול להיות בכל אחד משני הצירים, ומחוון בציר אחד היה משקר. במקומו — גרירה בשני הכיוונים, ומקשי חיצים לנגישות.

בלי תמונה, האות והצבע נשארים בדיוק כפי שהיו.
